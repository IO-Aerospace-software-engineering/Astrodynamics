# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

IO.Astrodynamics is a .NET 10 astrodynamics toolkit with a thin C++ interop layer for NASA/JPL NAIF CSPICE.

**The C++ layer** (`IO.Astrodynamics/`) is the bridge to CSPICE. The product is the .NET library, so features land in the .NET projects of `IO.Astrodynamics.Net/`; the C++ layer is changed when a technical or ergonomic reason calls for it (a CSPICE call the .NET side cannot make well, an error a proxy drops, performance), not to add features of its own (decided by S. Guillet, 2026-11-12). A change keeps the P/Invoke declarations of `SpiceAPI` and the native library of the same release in step, is built by `build-native` on the three platforms, and is tested by the C++ tests and the .NET tests that reach it.

## Commands

All .NET commands run from within `IO.Astrodynamics.Net/`:

```bash
# Build
dotnet build IO.Astrodynamics.sln

# Run all tests
dotnet test

# Run tests for a specific project
dotnet test IO.Astrodynamics.Tests/IO.Astrodynamics.Tests.csproj

# The LongValidation category (validations and studies of minutes each) is skipped unless IO_ASTRODYNAMICS_LONG_VALIDATION=1;
# the manual workflow long-validation.yml sets it, before each release and on a PR that changes the dynamics it measures
dotnet test --filter "Category!=LongValidation"

# Skip the Validation category too (bit-for-bit goldens, heavy validations), which CI runs on Linux only
dotnet test --filter "Category!=Validation&Category!=LongValidation"

# Run the LongValidation category (Linux, about 40 min on the CI runner: 39 min 17 s, tests 37.76 min, run 43603489238, 2026-11-14, after #669 and #670)
IO_ASTRODYNAMICS_LONG_VALIDATION=1 dotnet test IO.Astrodynamics.Tests/IO.Astrodynamics.Tests.csproj -c Release --filter "Category=LongValidation"

# Run a single test by name
dotnet test --filter "FullyQualifiedName~IO.Astrodynamics.Tests.ClassName.TestName"
dotnet test --filter "DisplayName~TLE"

# Run with coverage
dotnet test --collect:"XPlat Code Coverage"

# Run the CLI tool
dotnet run --project IO.Astrodynamics.CLI -- --help
```

C++ build (only needed when the native layer changes):
```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
```

## Architecture

### Two-Layer Design

```
IO.Astrodynamics/            ← C++: P/Invoke bridge to CSPICE, changed when a technical or ergonomic reason calls for it
IO.Astrodynamics.Net/        ← .NET: the product, where features land
  ├── IO.Astrodynamics/      ← Core library
  ├── IO.Astrodynamics.CLI/  ← CLI tool (astro command)
  ├── IO.Astrodynamics.Tests/
  ├── IO.Astrodynamics.CLI.Tests/
  └── IO.Astrodynamics.Performance/  ← BenchmarkDotNet benchmarks
```

The native bridge is accessed via `IO.Astrodynamics.SpiceAPI` (singleton, P/Invoke). All SPICE calls must go through the shared lock object — CSPICE is not thread-safe.

- `ReadOrientationProxy`, `ReadEphemerisProxy` and the five proxies of the CSPICE window searches (`FindWindowsOnDistanceConstraintProxy`, `FindWindowsOnOccultationConstraintProxy`, `FindWindowsOnCoordinateConstraintProxy`, `FindWindowsOnIlluminationConstraintProxy`, `FindWindowsInFieldOfViewConstraintProxy`; fourth round of #668, a native change for a technical reason: they dropped SPICE's error, and a search SPICE could not run returned no window) return `bool` (`true` = success, `false` = error, no window written), and `GetFrameNameProxy` (`frmnam_c`, #676) `false` when SPICE knows no frame of the id, `GetNaifIdProxy` (`bodn2c_c`, choice 12 of #668, behind the public `SpiceAPI.TryGetNaifId`) `false` when SPICE knows no body of the name, `GetFrameInfoProxy` (`namfrm_c`, `frinfo_c`, #593, a native change for a technical reason: the .NET side cannot read the centre and class of a frame) `false` when SPICE knows no frame of the name

## Critical Domain Rules

### Mean vs. Osculating Elements

### Force Model Defaults

- Drag coefficient (Cd) default: **2.2** (free-molecular flow), not 0.3
- Atmospheric drag uses **atmosphere-relative velocity** (body velocity minus co-rotation: `v_rel = v_body - omega × r_body`), with the atmosphere of the central body (#674): its model, or **NRLMSISE-00 at nominal space weather** for an Earth without one (internal `CelestialBody.Atmosphere`, `EarthDefaultAtmosphere`, one instance per thread; `HasAtmosphericModel` still means a model was given); another central body without a model throws `InvalidOperationException`, whatever the listed bodies; an Earth always has an atmosphere, so a listed Earth without a model adds that drag about any central body (decided by S. Guillet, 2026-11-14); about the Sun (SSB mode) the listed bodies with an atmosphere give the drag, and the run throws when none has one; `GetAtmosphere` and the context getters read the same atmosphere with a full context, and a model-less Earth answers an altitude-only or partial context (the altitude overloads included) with the U.S. Standard Atmosphere 1976 (`EarthDefaultAtmosphere.Standard`, one stateless instance shared by every thread), its base atmosphere, never read by drag (decided by S. Guillet, 2026-11-14); a null context and another body without a model give NaN, 0 and 0
- The central body takes part on every path with the observer's models, inserted first when not listed (#674); listed bodies of one NAIF identifier, the observer's included, must have equal GM, radii, gravitational field and atmospheric model (`CelestialItem.ModelDifference`, NRLMSISE-00 by switches and space weather), or the propagation and `Scenario.AddCelestialItem` throw `ArgumentException`; a value-equal twin of the observer runs with the observer's instance; a central body whose GM is not finite and above 0 (a body of the kernels without `BODYnnn_GM`, which `new CelestialBody(id)` accepts) throws `ArgumentException` (`spacecraft`) naming it, its `BODYnnn_GM` and `gm_de440.tpc`, on every path at the start of the propagation, before the integrator of an options path is built and claimed, after the claim of an integrator given to a constructor (decision 27 of lot L4) (internal `CentralBodyPropagator.RequireGravitationalParameter`, through `ResolveCentralBody`, the Sun of the SSB mode included; R03 of #668, structuring choice 10, decided by S. Guillet, 2026-11-19: before, it ran without central gravity)
- Third bodies (`ThirdBodyPerturbation`): Battin's form where the spacecraft is far from the perturbing body, the direct difference −μ ((r − d)/|r − d|³ + d/|d|³) where |r − d| < |d|/2 (SSB mode near a planet, near the Moon about the Earth), whose Battin 1 + q lost eight digits (#576, #544): a few ε of the exact acceleration everywhere, Battin's bit for bit elsewhere
- SRP reflectivity Cr comes from `Spacecraft.SolarRadiationCoeff` (typically 1.0 to 2.0; finite and not negative; default 1.0)
- SRP uses **continuous shadow fraction** (partial/annular eclipses scale SRP proportionally)
- Both forces use **dynamic mass** via `GetTotalMass()` (dry + fuel + payload)

### Time Argument

- A numerical propagation whose resolved central body is the Earth integrates over the TT seconds between the instants of its window (#501): the forces at t are those of TT₀ + t (bodies and orientation at its TDB, drag at its UTC). Any other central body, SSB mode included, integrates over TDB seconds, bit for bit as before
- Labels (segment bases, stages, events, outputs) stay TDB; `Duration`, `CumulativeTime`, the event time and the `IIntegrator` duration count the seconds of the argument; `AtEpoch`, `EpochAtMeanAnomaly`, Lambert and IOD count TT seconds about the Earth, TDB otherwise, whatever the tags (#508)
- The thrust window of an impulse is the equivalent constant-thrust burn whose acceleration has its centroid at the impulse epoch t (#335, derived from S. Guillet's remark of 2026-11-18 that the acceleration grows during the burn, decided by S. Guillet, 2026-11-18): [t − f dt, t + (1 − f) dt], dt by the rocket equation, f = 1/x + 1/ln(1 − x) for the mass fraction burned x (internal `ImpulseManeuver.ThrustLeadFraction`, 1/2 + u/12 − … below u = Δv/(Isp g0) = 0.1; 0.509 at x = 0.1, 0.557 at 0.5), in the execution (internal `TryExecute`) and the TT windows alike; a fixed 0.666 before 11.0.0. It sets `ManeuverWindow`, `MAN_EPOCH_IGNITION`, the opening of the impulse's attitude and the gate of the next maneuver; the propagated state takes the whole ΔV at t
- The maneuver chain counts the seconds of the argument (#547): about the Earth the thrust and maneuver windows of an impulse count TT seconds from the time argument of its event (τ, the sum of the event times), the hold of an attitude TT seconds from its activation; otherwise the TDB arithmetic of the maneuvers, bit for bit

### Minimum Epoch of an Impulse

- An impulse fires at the first crossing of its g-function in its direction at or after its `MinEpoch`, searched from the integrated state there (#569): `VVIntegrator` and `RK78Integrator` evaluate g at the gate in the step that holds it (internal `IGatedEventDetector`, `EventGates`; RK7(8) by a shortened step and a bisection over [gate, step end], Velocity-Verlet by the cubic Hermite of the step); a g exactly zero at the gate counts there when the sign after it is the target sign (inside a step, on a step end, at the base), and so does a g exactly zero at the base with the gate before it (GMAT's convention, #580); a g exactly zero at a step end after a non-zero one is a crossing there (#580), a zero at the base of a detector without a gate none (Hipparchus's convention); `PlaneAlignmentManeuver` takes the node it moves toward at the gate, and at the base when the gate is open there (`ComputeEventValueAtSearchStart`, #581). `IIntegrator.IntegrateSegment` reports one event per call, the earliest crossing of the step, ties in list order (#578); a Velocity-Verlet event is carried onto the tick of its label, its step integrated again to that time (#572); an impulse executed with no time left after it opens a last segment of zero length, so the solution ends with the state after it (#575); all decided by S. Guillet, 2026-11-17. The internal `ManeuverEventDetector.Evaluate` keeps its +1 before the gate (for a custom `IIntegrator`, which receives it as an `IEventDetector`), which the library's integrators never compare with a g-value after the gate (they replace it with the g-value at the gate); every step without a gate is unchanged. See `docs/reference/impulse-maneuvers.md#minimum-epoch`
- The gate of a chained maneuver, the end of the previous maneuver's window, belongs to one propagation (#573): `Spacecraft.ChainStandbyManeuver` raises `Maneuver.PropagationGate`, which `Maneuver.Reset` clears at the start of each propagation (`Spacecraft.ResetPropagation`, called by `PropagatorBase.Propagate` once its checks pass, on every path: `Spacecraft.Propagate` and a `CentralBodyPropagator` built directly, which re-arms the spacecraft, refuels its tanks, clears `ExecutedManeuvers`, its stored states and attitude record and makes it `IsPropagated`; a propagator built and never run changes nothing; #583, decided by S. Guillet, 2026-11-17: before, only `Spacecraft.Propagate` did); the public `SetManeuvers(params Maneuver[])` sets the plan (decisions 45 to 47 of #668, decided by S. Guillet, 2026-11-23: in order, each maneuver linked to the next, `NextManeuver`'s setter internal, read back by `Spacecraft.Maneuvers`, nothing added to `ExecutedManeuvers`, no maneuver clearing it, #584; `SetStandbyManeuver`, `SetNextManeuver` and `InitialManeuver` removed, the internal `StandbyManeuver` the run's state), claiming each maneuver for its spacecraft (`ArgumentException` for a maneuver of another spacecraft's plan, a duplicate, an engine not in the spacecraft's `Engines` (added with `AddEngine`, by reference, decision 92 of #668), an engine whose tank is not the spacecraft's or a target frame that differs; released when the owner sets another plan; a propagator built after the initial orbit's frame changed keeps its `ArgumentException` (`spacecraft`) for a target frame that differs, only `Propagate` re-checking the frames with `InvalidOperationException`, decision 94; the engines re-checked with `InvalidOperationException` when the propagator is built and at the run); `MinEpoch` is the later of the gate and the minimum epoch of the maneuver's constructor (`GivenMinEpoch`, which lasts; a later one is a new maneuver in a new plan), with no setter. The library's advances of a chain go through `ChainStandbyManeuver`, never `SetManeuvers`
- The attitude timeline raises gates too (#539): each executed attitude, leading or chained, raises the gate of the next maneuver to the end of its hold through `ChainStandbyManeuver` (the last leading hold gates the first impulse); about the Earth the TT end of an impulse's window replaces, through the internal overwrite `Maneuver.SetPropagationGate`, the TDB end the impulse's execution raised the next gate to (#547). `ManeuverEventDetector.HandleEvent` executes the impulse only and returns no next detector; the propagation advances the chain

### Thread Safety

- CSPICE P/Invoke calls: use shared lock — **not thread-safe**. No type initializer of the library reads SPICE: the static objects of `PlanetsAndMoons` (`EARTH_BODY`, `MOON_BODY`), `Stars` (`SUN_BODY`) and `Barycenters` read their provider data at the first read of a member that needs them (internal deferred mode of `CelestialItem`/`CelestialBody`, `Resolved`, `ItemProvider`), from the provider set at that time, retried on failure, published with a compare-exchange and never under a lock held across the provider call (second round of #668), so a thread holding the SPICE lock never waits on another; before, their initializers read SPICE, which deadlocked a thread holding the lock against a thread running the initializer (#623), and a missing datum of a `MemoryDataProvider` threw a `TypeInitializationException` kept for the process. A custom `IDataProvider` (the frames of an ephemeris read in TEME, CIRS or TIRS) runs under the lock, and `WriteEphemeris`/`WriteOrientation` enumerate the caller's states once, before it (#661); the two-body calls and element conversions of `SpiceAPI` hold it for their native call only and return the observer and frame instances of their input, reading no provider (#725, #664). `ColdStartTests` checks the paths fixed by #623 (`ConvertTleToStateVector`, `TLE.ToStateVector`, both `ReadEphemeris` overloads from L1, thread B reading a static object's GM) and `MemoryDataProviderBodyTests` the deferred static objects (modes `static-bodies-memory`, `static-bodies-spice`, `static-bodies-switch`, `static-bodies-before-kernels`) in fresh processes (`IO.Astrodynamics.Tests.ColdStart`)
- `GeopotentialGravitationalField`: **NOT thread-safe** — one instance per thread; every propagation that builds its forces builds its own field from the central body's model (internal `CelestialItem.CreatePropagationField`, R06 of #668, one field per run), so a `CelestialBody` with a geopotential is shared by concurrent propagations and their solutions, bit for bit separate bodies, its own field (`EvaluateGravitationalAcceleration`, a force list of one's own) one thread at a time; a `GeopotentialModelParameters` (a value) builds any number of bodies and propagations on any thread, its coefficients read once and shared read only (#674)
- `Nrlmsise00Model`: thread-safe, concurrent use OK, its calls serialized on a lock of the instance (a shared configured model serializes parallel propagations); the default atmosphere of a model-less Earth is one instance per thread
- Force partials (internal, `ForceBase.AccumulateStatePartials`): a force keeps a work `StateVector` for its finite differences, so the partials path of one force instance is **not reentrant**, unlike `Apply`. Forces belong to one integrator, as the propagator builds them
- Managed occultation, field-of-view and window (`GeometryFinder`) searches: no state, kernels read under the shared lock; searches on separate propagations may run concurrently
- Attitude record of a managed spacecraft (`SpacecraftFrame`): filled by its propagation only (and `AddStateOrientationToICRF`), read under a lock of the record; a read stores nothing (#523), so reads from any thread, before, during or after the propagation, leave the attitude and its CK unchanged. An ephemeris read in its frame rotates by the record under the shared SPICE lock (#682), so the record lock nests inside the SPICE lock: no region of the record lock may call SPICE. A kernel-backed spacecraft frame reads SPICE at each call, under the shared lock, and caches nothing: the frame the loaded kernels define for its id NaifId × 1000 whatever its name (`SpiceAPI.SpiceFrameName` through `GetFrameNameProxy`, its own name `Name + "_FRAME"` when none does, #676). So does the frame of a site from the kernels whose frame id (1000000 + NaifId) the loaded kernels define: that kernel frame, by its kernel name whatever the name of the site (when none does, the frame of its J2000 coordinates, an ephemeris read in it rotated as for a site from coordinates, third review of #690), on every path, `WriteFrame` included, which writes it as a TK matrix of the body frame (#690)
- `CelestialItem.Satellites`: safe across threads, its items held weakly and by instance (`WeakSatellites`, a `ConditionalWeakTable`), each listed at the end of its constructor (`RegisterWithObserver`), so a spacecraft referenced nowhere else leaves it after a collection (#676)
- `Frame` keeps no orientation per epoch (#541, decided by S. Guillet, 2026-11-17): a frame, read from the data provider or computed by the library (`CirsFrame`, `TirsFrame`, `TemeFrame`, the frame of a site from coordinates), keeps the orientation of its last epoch only, read again after a change of the kernel pool (internal `Frame.LastOrientation`, an immutable entry replaced as a whole, `SpiceAPI.KernelPoolGeneration`), and the attitude record API (`AddStateOrientationToICRF`, `GetStateOrientationsToICRF`, `GetLatestStateOrientationToICRF`, `ClearStateOrientations`) is `SpacecraftFrame`'s
- Frame orientation cache: active only on the thread that propagates or evaluates a propagation (`Frame.UseOrientationCache`), never set on the shared `Frame`; propagations and RK7(8) evaluations sharing a central body without a geopotential may run concurrently. It interpolates its 60 s grid by the exact SLERP (#561); it and the ephemeris cache cover the span the propagation integrates, its window (internal `PropagatorBase.PropagationSpan`, #626; to round(L/ΔT)·ΔT, up to ΔT/2 past the window, before choice 6 of #668), and a read outside either grid reads the data provider at its epoch
- RK7(8) evaluations after a propagation (`PropagationSolution.GetStateVector`, `GetStateTransitionMatrix`, `GetParameterSensitivity`, `GetCovariance`, `GetExtendedCovariance`, and the internal `InterpolateAt`, `EvaluateVariational`, `EvaluateCovariance` and `EvaluateExtendedCovariance`): serialized by one lock per propagator instance (internal `PropagatorBase.DynamicsSyncRoot`), shared by the solutions of all its runs (the dynamics of an RK7(8) solution, the force model of an RK7(8) or Velocity-Verlet one) and held by each of its runs for the whole run, user forces included, so the runs of the instance, two concurrent `Propagate` calls on it and the evaluations of its earlier solutions serialize (#782, decisions 25 and 28 of lot L4; a lock per solution before); they evaluate the forces of their propagation, its own geopotential field included (R06 of #668). Code a run calls (a `ForceBase`, a bare `IIntegrator`) must not evaluate the solution of another propagator that may be running: two reused instances whose forces evaluate each other's earlier solutions deadlock (the library evaluates no solution under the SPICE lock or the record lock, so it cannot deadlock by itself); an evaluation of an earlier solution waits for the end of a running run of the instance; a `Propagate` waiting for the lock reads its token once it holds it (`docs/guides/thread-safety.md#the-lock-of-a-propagator-instance`)
- An integrator belongs to one propagator (#782, decision 24 of lot L4): a second propagator given it throws `ArgumentException` (`integrator`), so no two propagators share an integrator, nor its time argument or variational equations; the claim is on the integrator, not on its forces: a force instance added to two integrators is not refused (the library adds the forces of a participant's propagation to the integrators of its avoidance options and of its non-linearity index, under the lock of that propagation)
- One run at a time per spacecraft (decision 43 of #668, decided by S. Guillet, 2026-11-23): every run re-arms its spacecraft and writes its states, attitude record, tanks and `ExecutedManeuvers` on it, and the lock a run holds is its propagator instance's, so two runs on one spacecraft through different paths (two propagators, `Spacecraft.Propagate`, a `TLEPropagator`, a scenario or a batch beside a direct run) interleave silently and can charge a burn twice; `BatchPropagator` refuses a spacecraft in two of its tasks only; the plan of a spacecraft is not changed during a run on it (decision 96 of #668, decided by S. Guillet, 2026-11-24: a run reads the plan as it goes, and the plan [m1, m2] set again mid-run left `ExecutedManeuvers` reading m1, m1); a run guard (`InvalidOperationException` before anything changes) comes after L5 (#793), refusing a second run and `SetManeuvers` while a run holds the spacecraft; the kernels of a spacecraft (`WriteKernels`, `WriteEphemeris`, `WriteOrientation`, the Cosmographia export) are written outside a run on it, and `WriteKernels` holds the shared SPICE lock from its load-scope checks to its last load (the record lock nesting inside it), so two calls on two spacecraft serialize and both succeed; `docs/guides/thread-safety.md#one-run-at-a-time-per-spacecraft`
- Conjunction analysis with a propagated covariance (`ConjunctionAssessment.Analyze`, `AnalyzeAll`) and `EvaluateAvoidance`: the replay of the variational equations, the propagations of the non-linearity index and of the avoidance options (with or without a propagated covariance, RK7(8) or Velocity-Verlet) use the forces of the participant's propagation under the lock of the forces of its propagator (`DynamicsSyncRoot`), which its solution and the force model its spacecraft keeps carry, with the same rule

## Validation and Thresholds

Rules learned during the state transition matrix and covariance work (10.2.0-preview-1, tracking issue #364 and its "Lessons learned"):

- Expected values come from SPICE or an independent reference (GMAT, a closed form, an extended-precision computation), never from a snapshot of the code. A golden is recaptured only for an intended change of results, which the PR states.
- A reference about the Earth counts TT seconds between its epochs (`PropagationTimeArgument.Tt.SecondsBetween`, or an exact elapsed time through `InterpolateAtElapsed`), never a TDB epoch difference; the SPICE occultation references of `tools/occultation_reference`, which count ET within their bounds, are the stated exception.
- A reference must resolve better than what it measures. Central differences of whole propagations take a tolerance of 1e-14 and start from the exact perturbed state; a sensitivity at the noise floor (Ψ_Cr) is measured against the same propagation with the variational equations in the step control. Otherwise the test measures its reference.
- Thresholds are set from a measurement and never relaxed to make a test pass: a failing test is first a bug to understand. A record at the noise level is twice the worst value over Linux, Windows and macOS arm64, read from the CI logs (integration noise differs between platforms); a figure measured on Linux alone has already failed on macOS arm64.
- Test every combination the public surface allows: both integrators, every activation path, participants propagated or not, maneuvers, SSB mode, a non-ICRF frame. Test a new coordinate rule where its coordinates are singular (poles, polar axis, equator).
- A defect found outside the scope of a change gets its own issue and its own PR; the change is not widened.
- A change of the dynamics is checked by the manual workflow `long-validation.yml`, never in a session container, and by `gmat-reference.yml` when what GMAT reads changes. A published figure that a change moves is measured again in the same PR.
